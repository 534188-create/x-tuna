# Контекст x-tuna

## Паспорт проекта

Репозиторий: 534188-create/x-tuna. Постконфигуратор установленной панели LucX для Debian 12/13. Рантайм — стандартная библиотека Python 3.11+. Основные команды — x-tuna и lucx-post-configure.

## Цели и границы

Настройка внешних доменов, маршрутов, сайтов-заглушек, подписок, сертификатов и сетевых параметров. Панель LucX и подключения создаются до запуска x-tuna. Документация описывает текущие команды и действия пользователя; README содержит назначение программы, требования и быстрый старт.

Диагностические пробы имеют ограничения охвата. Работу VPN подтверждает подключение реального клиента, а не только состояние служб или успешная отправка тестового пакета.

## Неподвижные инварианты

Исходный Naive Caddyfile не редактируется x-tuna. Действующие credentials/клиенты и внутренние listener-порты сохраняются. qWDTT исключается из подписок, TrustTunnel публикуется как HTTPS/h2. VPN-маршрут имеет приоритет над сайтом. Неоднозначные конфигурации нельзя объявлять подтверждёнными. Секреты и реальные адреса не входят в репозиторий.

## Жизненный цикл применения

Основной путь Engine: аудит → план → backup → staging → validation → commit → health-check → rollback при ошибке. Конкретные проверки зависят от выбранных компонентов и режима полной приёмки. Network tuning использует отдельный sysctl-путь; нельзя описывать его как полную копию Engine-транзакции. Перезагрузка — отдельное действие с двойным подтверждением.

## Публичные маршруты начального мастера

В LucX `lucx.230` публичный адрес и порт задаются записью Host. При отсутствии Host поле `share_addr` определяет только адрес: порт в исходной подписке остаётся внутренним. Значение `домен:порт` в этом поле приводит к некорректной URL authority. Подтверждённая публикация требует отдельной записи Host и чистого домена в `share_addr`; исходные credentials, TLS/SNI и listener-порты сохраняются. Создание новой записи должно проходить точный контроль receipt, повторного аудита и отката; неподтверждённая схема и конфликтующие legacy overrides блокируют запись.

Запись Host не назначает протокол клиенту. Включение inbound в подписку определяется существующей связью `client_inbounds`; отсутствие этой связи нельзя исправлять изменением клиентов во время публикации маршрутов.

Для VLESS/Trojan Reality с несколькими именами SNI аудит сохраняет полный `inherited_sni_names` в одной физической записи endpoint. Рендерер маршрутизирует каждое имя только после проверки полного подтверждённого набора. Явный blank, неизвестная неоднозначность и неполный набор блокируются. Для TrustTunnel источник SNI — `settings.hostname`, а не адрес подключения. Автоматические VPN-пробы со скалярным SNI не считают набор проверенным; работу клиента подтверждает отдельная клиентская проверка.

При формировании HAProxy заявки `tcp_side_site` с назначением `site` добавляются после подтверждённых маршрутов. Если пара TCP-порт/SNI уже обслуживается VPN или его браузерным разделителем, отдельная заявка сайта её не заменяет. Это позволяет TrustTunnel и прямому qWDTT использовать один домен, сохраняя отдельный listener qWDTT и приоритет VPN на TCP/443. Заявки с назначением `vpn` сохраняют строгую проверку конфликтов. Тесты проверяют оба порядка протоколов, отказ при двух VPN-владельцах и независимость маршрутов одного SNI на разных портах.

После выбора публичных портов начальный мастер передаёт подтверждённый черновик в `configure_decoy_routing_mode` с `refresh_from_audit=False`. Классификация использует свежий аудит, но не подменяет выбранные публичные порты, SNI и разрешения публикации прежними адресами LucX. Это относится и к повторной классификации после подтверждения XHTTP path. Внутренние listener-порты остаются прежними.

Для обновления существующего манифеста `refresh_from_audit=True` остаётся значением по умолчанию. Регрессионные тесты проходят весь начальный мастер для VLESS, Trojan, Naive, TrustTunnel и AnyTLS; отдельно проверяются повторный вызов для XHTTP и прежний контракт обновления по аудиту.

## Naive на отдельном порту

При стратегии `tcp_side_site` Naive сохраняет свой listener, а браузерный сайт использует общий TCP-порт. Рендерер заново определяет эту стратегию по текущим параметрам и не требует содержимое Caddyfile для независимого сайта. Сохранённый план проверяется полностью; подмена стратегии или конфликт портов блокирует генерацию. Для native, managed и CONNECT-маршрутов требования к исходному Caddyfile сохраняются.

Регрессионные проверки покрывают генерацию сайта, сохранение параметров протокола, отклонение устаревшего плана и достижение предварительного backup через Engine. Проверка границы backup останавливается до staging и commit и не заменяет испытание VPN-клиентом.

При перезапуске LucX сама панель может перегенерировать свой Caddyfile. В режиме `RouteThroughXray` функция `SocksBridgeAuth` создаёт случайный пароль внутреннего SOCKS-моста один раз на процесс. Поэтому изменение хеша после перезапуска не доказывает изменение клиентских credentials, но его нельзя называть побайтным сохранением исходника. x-tuna не записывает и не восстанавливает этот файл; отдельно сверяются его тип, владелец, режим, сохранённые настройки и согласованность действующего моста.

## Поколения Naive и повторная проверка

Поиск записей продления ACME принимает только `<domain>/<domain>.conf` и `<domain>_ecc/<domain>.conf`. Соседние OpenSSL `*.csr.conf` и служебные конфигурации не разбираются как записи продления; повреждённая доменная запись по-прежнему блокирует операцию.

Перед показом плана TUI, CLI и repair обновляют только производные сведения о проверенном поколении Naive. Привязка включает полный набор авторизации из LucX, endpoint, TLS-пути, строгую структуру исходного файла и объявленный runtime Xray. Отдельный отпечаток эпохи процесса отличает restart от перезаписи конфигурации при прежнем процессе. Изменение исходника после подтверждения по-прежнему останавливает commit.

Валидатор поколения распознаёт штатный относительный путь журнала LucX `bin/tunnel/naive-<id>-data/access.json`. Для проверки структуры используется нейтральное абсолютное представление; исходный путь сохраняется в семантическом отпечатке, файл журнала не читается и не записывается. Другие относительные пути и переходы `..` не принимаются. Строгий parser native/CONNECT не ослабляется.

При поиске процесса Xray процессы других владельцев пропускаются до чтения `comm`. Исполняемый файл выбранного Xray по-прежнему проверяется; небезопасный владелец или разрешение записи показываются отдельной причиной с указанием проверить происхождение бинарника и восстановить владельца root и режим 0755. Исходный Caddyfile для этого не меняется.

После разрешённого restart/reload выполняются ограниченное ожидание согласованного поколения, проверка управляемой копии и финальный health-check. Фоновый worker использует ту же блокировку Engine; он не запускается через `ExecStartPre` управляемого Caddy. Обновление копии проходит backup, staging с проверкой Caddy, CAS, атомарную запись с режимом 0600, restart/health и сохранение новых `installed_hashes`. Ошибки возвращают ненулевой статус без вывода credentials; откат не перезаписывает конкурентные изменения. Исходный Caddyfile не является целью записи или восстановления.

Состояния без `naive_generations` требуют явного плана первой привязки. Он честно принимает проверенную текущую БД как базу: историческое отсутствие изменений клиентской авторизации из прежних неполных отпечатков недоказуемо. Фоновый worker такую миграцию не выполняет. После привязки изменённые защищённые поля блокируют повторную попытку.

Регистрация существующего сертификата acme.sh выполняется отдельной операцией Engine: точная пара сертификат/ключ, проверенный hook, backup/CAS записи ACME и состояние после reload/health. Меняется только поле `Le_ReloadCmd`; пути назначения сертификатов сохраняются. Полный SQL/routing apply для этой команды не запускается. Меню автоматически читает root crontab, `/etc/crontab` и `/etc/cron.d`, проверяет точную команду acme.sh и состояние `cron.service`. Простое ежедневное расписание отображается временем запуска; для остальных поддержанных выражений показан cron. Часовой пояс берётся из проверенного `/etc/timezone`. Отсутствие задания, недоступность источника, неподдерживаемая запись и неактивная служба различаются. Само задание при диагностике не запускается.

Главное меню содержит пункт 6 «Повторно проверить и подготовить новый план». При отказе сохраняется исходное действие в текущем сеансе; повторение требует свежего preview и цифрового подтверждения. Активная блокировка не удаляется, проверки клиентов, портов и источников не отключаются.

Переход после reload выполняется с отдельным заданием `systemd-run --no-block` для каждого управляемого Naive inbound.

Уникальное имя каждого запуска исключает конфликт повторных синхронизаций, а проверка идёт по штатному порядку Engine с блокировкой и валидацией состояния.

Чтение SQLite учитывает повторное использование WAL после checkpoint: хвост может быть длиннее подтверждённой границы commit в SHM. Полная проверка выполняется в приватной копии; исходные DB/WAL/SHM используются только для чтения, и отклоняются неполный WAL, несовпадение native recovery или невалидный checksum.

## Подписки

Sidecar необязателен и требует отдельного выбора. Согласованные Host/path/формат клиента определяют выдачу. qWDTT и TrustTunnel QUIC/HTTP3 не должны попадать в экспортируемые профили. Полная ссылка подписки является приватной. Подробнее: [подписки](SUBSCRIPTIONS_RU.md).

## Обновление LucX и восстановление

Обновление панели, обновление x-tuna и ремонт внешних маршрутов — разные действия. Worker обновления LucX может продолжать свою операцию отдельно от интерактивной сессии; проверяйте его статус. Resume повторяет сохранённый манифест. Откат управляемых файлов не заменяет снимок всей VPS.

## Тестовые ворота

Compileall, unittest, проверка документации и секретов, две детерминированные сборки, shell syntax и diff check обязательны перед публикацией. Результаты записываются в [описание поставки](RELEASE_RU.md). Неисправленный падающий тест нельзя считать пройденным по сообщению о работающем сервере.
